Measuring the midsesh chat, with the data you already keep

What ships, and what it already records

Review findings

Ordered by how much each one limits what you can learn once traffic arrives.

Strength

The funnel is mostly already in the database

lib/supabase.ts, lib/insights.ts

Sessions, messages with a question number, searches, and leads are all persisted server-side, keyed by sessionId, with referrer and flow on every session. That means most of the funnel can be reconstructed post-hoc with SQL, no new tracking code in the chat.

Right now the only thing reading these rows is a daily email report (app/api/report/route.ts) that covers counts, errors, latency, and SerpAPI quota. It does not draw a funnel or a conversion rate.

Use it: the fastest analytics here is querying rows you already have, not adding a tool. Start with SQL views over sessions, messages, searches, and leads.
Key gap

The three highest-intent steps never reach the server

components/Chat.tsx

The chat phase machine goes welcome → chat → searching → matches → email → done, but only some phases write a row. Seeing the expert cards (matches), selecting who to meet, and opening the email form all live in browser state and vanish if the person leaves.

So you can see that a search ran and whether a lead came in, but not the drop between them: how many people saw real matches and still did not request an intro. That is the most valuable question in the whole funnel, and today it is invisible.

Fix (chosen: PostHog): emit a PostHog capture on each phase transition, with all inputs masked. The steps are already named in Chat.tsx, so this is a handful of lines: matches_shown, experts_selected, email_shown, intro_submitted, plus choice_shown and install_clicked for the dev flow. These same events power the funnel and the replay filter.
High

No product analytics means no replay and no self-serve funnels

whole app

There is no PostHog, GA, or similar in the chat. SQL gives you counts, but not the things that explain them: watching a real conversation stall, seeing rage clicks on a chip, or splitting the funnel by referrer without writing a new query each time.

Fix: add PostHog to the chat, with all inputs masked so emails and messages are never recorded in replay. Capture the same phase events as above. You get funnels, replay, and attribution for roughly ten lines plus the snippet. Decide a consent posture before this scales, since the chat is EU-reachable.
High

Demo mode will quietly poison every early number

lib/demo.ts, searches.demo

Until ANTHROPIC_API_KEY and SERPAPI_KEY are set in Vercel, chat and search serve scripted demo replies. Searches carry a demo flag, but sessions and leads do not, so a demo conversation looks like a real one in the funnel.

Fix: stamp a demo boolean on the session row too, and filter it out of every chart by default. Until the keys are live, treat all funnel numbers as staging, not signal.
Medium

What people actually want is logged, but not queryable

lib/insights.ts

Every completed brief has rich structure: expert type, domain, budget, timeline, engagement shape. But recordInsight sends it to the server log and an optional webhook, not to a table. So "what are people asking for" and "what budgets show up" cannot be charted from Supabase as things stand.

Fix: also write briefs to a briefs table. Then the demand-mix and budget charts below become simple queries.
Medium

One session per visit, by design, so no returning-visitor view

components/Chat.tsx: newSessionId

The sessionId is generated per page load with no cookie or storage. That is a clean privacy choice, and it means retention and returning-visitor charts are not possible without adding a persistent id. Worth naming so nobody builds a retention chart on sand.

Decision, not a bug: keep it for launch. If retention becomes a question later, add an opt-in first-party id, and make that a deliberate call.
Note

What is already solid

good hygiene

The ops layer is done well: withMetrics records latency and status for every route, the daily report flags 5xx errors and SerpAPI quota, and purge_expired handles retention. Referrer is captured on sessions, so channel attribution works post-hoc. Rate limiting and origin checks are in place. None of this needs rebuilding.

Order of work

Cheapest signal first. Phase 0 needs no new code in the chat.

Phase 0

Chart what you already store

  • SQL views over sessions, messages, searches, leads for the funnel-so-far, question drop-off, conversion rate, and referrer.
  • Filter demo out using searches.demo, and add a demo flag to sessions so the filter is reliable.
  • Surface it: a small password-gated /admin page in the Next.js app renders these views. In-repo, owned by you, no third-party tool for the core funnel. (Chosen path.)
Phase 1

Close the funnel with phase events

  • Emit events on matches_shown, experts_selected, email_shown, intro_submitted, plus choice_shown and install_clicked for the dev flow.
  • Add PostHog to the chat with inputs masked, so the same events power funnels and replay, and settle the consent posture.
Phase 2

Make demand queryable

  • Write briefs to a table so expert type, budget, and timeline can be charted.
  • Build the demand and budget charts, segmented by flow.
Phase 3

Dashboard and a weekly habit

  • One dashboard with the charts above, main and dev split.
  • One weekly read: worst funnel step, question people quit on, conversion trend. Then one change.
